SeoulFit · backend

How a chat message becomes an itinerary

SeoulFit takes a free-text trip request and returns a day-by-day Seoul itinerary that has been retrieved from curated courses, drafted by Gemini, repaired deterministically, and then scored by a critic before it ships. Three views of that system, with the thresholds and function names it actually runs on.

View one · the request path

The pipeline, input to itinerary

One POST /chat at a time. The intake turn repeats until the traveller types confirm; everything after that runs in a single pass and lands back in the same checkpointed state the next turn will read.

01

Slot intake

A NeMo self-check rail screens the message and fails open on any error. Gemini then pulls six slots out of free text — dates, interests, restrictions, companion, pace, area — in JSON mode. A reply that will not parse is fed back to the model once, quoted verbatim, with an instruction to return valid JSON; a second failure yields an empty object rather than an apology. The agent summarises and waits, and this turn repeats until the traveller confirms.

graph.py collect · confirm · handle_confirm  ·  guardrail_gate.py is_blocked

02

Segmented retrieval

The trip is cut into per-area, per-purpose day segments before anything is searched, so “two days Hongdae plus one day historical” never collapses into one blended query. Each segment runs its own vector search, over-fetches three times what it needs, and then pushes courses whose stops sit outside the requested neighbourhood below the ones that don't. 03

Plan generation

Google Places fills the gaps the curated courses leave — cafés, meals, K-POP, shopping — per requested area. Anchors and supplements go into the planner prompt together. What comes back is parsed through a three-step ladder, then checked against the candidate pool by six deterministic passes that the model never sees. The passes →

Critique and return

The critic scores four things, the repairer patches what it can, and the critic scores again. Both reports travel with the itinerary, so a reader can see what was wrong before it was fixed. Day routes are re-ordered and transit legs computed last. The scoring →

View two · retrieval and grounding

What the RAG half actually does

Two lanes meet at the index. The lower lane is built once, offline; the upper lane runs on every confirmed trip. Nothing in the corpus is split below the level of a single curated course.

Lower lane: offline index build·Upper lane: per-request retrieval

Chunking

There is no token-window splitter and no overlap. The retrieval unit is one editorially curated Seoul course, and it is never cut smaller.

_course_to_text
Flattens a course into one searchable string: Title, Source, Themes, then one line per stop as - (type) name — address. That string, whole, is the embedded page_content.
_course_to_document
Wraps it as a LangChain Document and attaches course_id, source, source_url, course_title, themes, poi_count, total_estimated_minutes — and the entire raw course dict.
Why it matters
Because the whole record rides in the metadata, a hit returns the full structured course with its stop sequence and coordinates, not a text snippet the planner would have to re-parse.

Building the index

Model
gemini-embedding-001 through GoogleGenerativeAIEmbeddings.
Batching
50 documents per call, then sleep(60) before the next batch — sized for the free-tier rate limit, not for throughput.
Backoff
Up to 5 attempts. On a 429 the server's own retry_delay is parsed out of the error text and slept for, plus one second; if it isn't there, 60 seconds. Anything that isn't a quota error re-raises immediately.
Persistence
FAISS.from_embeddings then save_local → vectorstore/index.faiss and index.pkl. Reloaded with allow_dangerous_deserialization=True and held as a module singleton keyed on the API key, so it is read from disk once per process.

Turning a trip into queries

Day count
Tried in order: N week × 7 → N days or N일 → N nights or N박 → an inclusive date-range span → a lone calendar date, which is one day → a bare number, but only if it falls between 1 and 30. The order is what stops “June 23” from becoming a 23-day trip.
Date ranges
ISO pairs are matched before any dash-splitting, so 2026-06-23 is never torn into 2026 and 23. Month-name and bare day ranges fall through to dateutil, which carries the start month onto a bare end day; a negative span is read as crossing into the next month. Spans outside 1–60 days are rejected.
Areas
extract_requested_areas reads both the location and the purpose text, so an area named only in “K-pop spots in Hongdae” is still found.
Purpose per area
_split_purpose_by_area splits the purpose on and, then, commas and semicolons, then attaches each clause to the area whose alias appears inside it. An area no clause mentions inherits the whole purpose string.
Day allocation
Days are dealt out evenly across areas, and the last area absorbs the remainder, so every day belongs to exactly one segment.

Breadth, and the re-rank

k per segment
max(2, min(6, days + 1)). A five-day area asks for six anchor courses; a one-day area asks for two. A fixed k starved long segments into heavy Google padding and over-fetched short ones.
Query string
"{area label} {purpose hint} Seoul travel itinerary", built fresh per segment.
Over-fetch
similarity_search(query, k = k × 3). The extra two thirds exist purely so the re-rank has something to demote.
Dedupe
Candidates are collapsed on course_id with vector rank preserved, both within a segment and again across segments when the flat retrieved_courses list is assembled.
Re-rank
A stable partition, not a re-score: courses with at least one stop in the requested area sort ahead of those without, and vector order survives inside each group. A strong theme word like “K-pop” can otherwise float an off-neighbourhood course to the top.
Area matching
An exact name match, or one of the walkably adjacent sets — Hongdae with Hapjeong, Mangwon, Yeonnam and Mapo; Seongsu with Wangsimni; Gangnam with Sinsa and Garosu-gil; Jongno with Insadong and Myeongdong. With no name to go on, the nearest area centre within 3.2 km wins.

Filling the gaps with Google Places

Curated courses carry sights, not meals. The supplement runs per requested area and is deliberately conditional — most branches only fire if the traveller's stated purpose asks for them.

Restaurants
Always. Nearby Search, type=restaurant, 1800 m, rating ≥ 4.0, at most 5. Under three hits, a Text Search for "popular restaurants in {area} Seoul" at 2500 m tops it up.
Cafés
Only when the purpose mentions cafe, coffee, relax or 카페. 1800 m, rating ≥ 4.1 — a notch above the restaurant bar.
K-POP
Only on kpop, k-pop, bts, blackpink, idol or 아이돌.
Shopping
Only on shopping, shop, fashion or 쇼핑. type=shopping_mall, 2200 m, at most 3.
Long tail
Anything else — K-beauty, art, nature, nightlife — gets one Text Search for the purpose itself. Because Text Search treats radius as a bias rather than a filter, every hit's true area is re-derived from its coordinates and dropped unless it lands in or beside the requested area. Without that, an off-neighbourhood result would inflate the coverage score.
Stay times
Stamped by type, since Places doesn't supply them: café 45 minutes, restaurant 60, shopping mall 75, everything else 60.
Dedupe
Normalised name plus latitude and longitude rounded to four decimals — roughly 11 metres — so the same place found by two searches collapses into one.

View three · after the model replies

Parsing, repair and scoring

Everything between Gemini's reply and the itinerary the app receives is deterministic. The model gets one chance to fix its own JSON and no say at all in what happens next.

Getting to valid JSON

1 · Isolate
Strip markdown fences, then keep everything between the first { and the last }. Parse.
2 · Repair
Normalise smart quotes to straight ones, drop trailing commas before } or ]. Parse again.
3 · Ask the model
Only now: hand the first 8000 characters back with the parser's error and ask for the corrected object. If that fails too, the raw reply is written to planner_last_failed.txt and the error propagates.

The six validation passes

These run against the candidate pool — the retrieved courses plus the Google supplement — and are the reason a hallucinated stop cannot reach the app.

0

Pad and cap the days. Missing day numbers are added as empty days. If the planner over-produced — 22 days for a two-day trip is a real case — the extras are cut and their stops folded back round-robin into the days that remain, then renumbered contiguously. Nothing is dropped.

1

Delete hallucinations. Any stop whose normalised name is absent from the pool is removed and logged. Survivors are rewritten from the canonical record, keeping only the model's notes.

2

Force area coverage. Every requested area must appear at least twice. Short areas get candidates inserted into the day that maps to them.

3

Guarantee a meal. A day with no restaurant or café gets one inserted at position min(2, len) — around midday rather than tacked onto the end.

4

Fill thin days. Days are topped up to five stops from the same area, then from anywhere that doesn't belong to a different requested area.

5

Name the day. A theme still reading as a bare Day N is replaced with a generated one. Titles the model wrote are never overwritten.

6

Attach transit. Haversine distance between consecutive stops, walking at 4 km/h, driving at 30 km/h, plus a Kakao Map deep link per leg.

How the critic scores

ComponentWeightComputed as
Day feasibility0.35 1 − penalties ÷ days. Per day: −0.35 under five stops, −0.25 with no meal, −0.20 when the two furthest stops are more than 8 km apart.
Area coverage0.35 Areas holding at least two stops, divided by areas asked for.
Duplicates0.15 0.85 if any stop repeats across the trip, otherwise 1.00.
Foreigner readiness0.15 1 − ratio × 0.5, where a stop counts as risky with no English support, cash only, or cultural friction, and a low-confidence label adds 0.25. Flagged as an issue once the ratio reaches 0.4.

The repairer then re-covers thin areas, inserts missing meals, tops up under-filled days and strips duplicates, after which the critic runs again on the patched itinerary. Both scores and the repair log ship inside itinerary.critic_report.

The architecture behind that path

The same pipeline seen as components rather than as a sequence. Four of them sit inside one LangGraph state machine; the rest are the surfaces and services around it.

The dashed enclosure is the StateGraph — everything inside it shares one checkpointed TravelState

Client

The Flutter app. Talks to one FastAPI process over REST.

Python modules

API, agent, retrieval, planner, critic — plus the Lens and Live Help routers.

Local index

A FAISS store over the curated course dataset, built ahead of time.

Model

Gemini, used three ways: slot extraction, embeddings, itinerary drafting.

Gate

The NeMo input rail. The only thing that can stop a message reaching the planner.

Third party

Google Places for the planner; TourAPI, E-Gen and ODsay behind Live Help.
